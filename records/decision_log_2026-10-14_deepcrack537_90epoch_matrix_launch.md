## 2. 为什么是 66 支而不是 33 支

**P5、P6、P7 比的都是"换骨干增益"（ResNet18 减 UNet）或"跨骨干排名"，
所以 90 轮必须两个骨干都跑**，只跑一个则三条预测一条都判不了。

| 项 | 值 |
|---|---|
| 骨干 | `unet` 与 `pool_adapter_resnet18_unet` |
| 算子 | 11 个互异算子 |
| 种子 | 2026、2027、2028 |
| 支数 | **2 × 11 × 3 = 66** |
| 轮数 | 90 |
| 其余设置 | 逐项沿用 30 轮矩阵：base32 / lr 1e-3 / wd 1e-4 / 5 轮 warmup / bf16 AMP / group norm / 拖尾 MA(5) 选点 |
| run 名前缀 | `b90_<骨干>_gr_deepcrack537_…`，与既有 run 零冲突（已核对） |
| 启动时刻 | 2026-10-14 16:21，分离进程 |
| 日志 | `runs/_logs/b90_dc537_<stamp>.log` 与 `b90_dc537_stdout.log` |

### 2.1 跑的顺序是按判据的信息量排的

**算子为主序、骨干为次序**，且算子不按字母序，按对判据的信息量：

`min` → `btsp` → 其余按对下尾的依赖度递减。

**P6 只用到 `min` 与 `btsp`**，这两个算子的 12 支排在最前，
因此约 3 小时后即可先判 P6，不必等整批跑完。
P5 的 Spearman 则随算子逐个成形。

### 5.1 一条执行纪律，由上次的错写在这里

S14 §2.1 记过一次：我把判据里的"显著大于"写成裸不等式 `a > b`，
于是 0.0053 > 0.0050 判成满足，按种子配对重算后翻转为不满足。

**所以本轮判 P6 时，"3/3 同号"必须按种子配对逐个算符号，
不得用均值之差的符号代替。** P5 的 Spearman 同样按算子的增益均值算，
但须一并报告每个算子的逐种子符号一致性。
